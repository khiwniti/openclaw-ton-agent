  1. ROOT CAUSE: Closing Logic Bug (30+ min positions stuck)

  I found the bug. There are two interlocking issues:

  Bug A — time_stop check is LAST in precedence (decide.ts:243)

  In stepPosition(), the time-stop check is at the very bottom of the exit
  precedence chain. The order is:
  ladder_exit → partial_tp → trend_reversal → break_even/trail → tp → sl →
  time_stop

  The problem: for a sniping position that never hit its high-water mark (price
  went sideways or slightly down), trailingStopTon stays null (line 87: only
  arms when highWaterTon > pos.entryTon). This means the effectiveStop =
  -Infinity, so trail/break-even never fire. The position sits waiting for price
  to never come, and time_stop is checked last but...

  Bug B — Position reconstructed from orders journal with WRONG entryTs 
  (continuous.ts:110)

  On restart/boot, positions are reconstructed from the orders journal (lines
  95–121). The entry timestamp is set to ord.ts || Date.now(). But ord.ts is the
  order submission time, not the fill time. If the order object doesn't have ts
  populated correctly, it falls back to Date.now() — resetting the clock on 
  every restart. So a 35-minute-old position gets reconstructed with entryTs = 
  now, and the 30-minute time-stop never fires because the clock keeps getting
  reset.

  Bug C — stepPosition called with stale pos.entryTs after bounce 
  (continuous.ts:368–386)

  When a sell bounces (not zero-balance, not manual override), line 369 updates
  bounceCount but step.pos already has updated highWaterTon/trailingStopTon. The
  next poll evaluates step.pos again via openPositionsMap.get(address) — but
  step.pos.entryTs is from the original position, so that part is fine. However,
  the bounce count logic means a bouncing position can hold for 3 cycles × 
  5-second poll = 15 seconds before force-clear, which is acceptable. The real
  issue is Bug B.

  Bug D — Price fetch failure silently uses pos.entryTon as current price 
  (continuous.ts:277–289)

  If the STON.fi API call fails (network timeout, etc.), currentPriceTon = 
  pos.entryTon. This means stepPosition sees "price == entry" — so trailing stop
  never arms (needs highWaterTon > entryTon), TP never hits, SL never triggers.
  The position is effectively frozen whenever the price API is unreachable. The
  time_stop would still fire... if Bug B wasn't also present.

  2. Other System Gaps

  Gap E — pos.qty used in sell order but never set (continuous.ts:337)

  expectedTokenQty: pos.qty,
  Position.qty is not set anywhere in the openPosition() call on buy (lines
  213–230). It will be undefined → 0. The sell order goes out with
  expectedTokenQty: 0, which makes minOutTokenQty: 0 (no slippage protection on
  exits).

  Gap F — STON.fi V1 vs V2 ambiguity

  The acton-wallet.ts hardcodes STON.fi V1 opcode 0x25938561 and V1 router.
  STON.fi V2 (Ston.fi API v1 returns V2 pools by default). If a token only has a
  V2 pool, the swap silently fails pool-active check or routes to a dead pool.

  Gap G — No DEX aggregation / best-route selection

  Currently the system buys and sells exclusively on STON.fi V1, with DeDust as
  an optional path in router.ts but toSwapPayload() in acton-wallet hardcodes
  dex: "stonfi" (line 158). The DEX selection logic in router.ts / executeSwap()
  is never actually called from acton-wallet.ts — it's dead code for the hot
  path.

  Gap H — Sell gas value too low for DeDust (router.ts:790)

  DeDust sell uses toNano("0.35") as msg value but acton-wallet sell uses
  toNano("0.20"). On congested mainnet, 0.20 TON is borderline for jetton
  transfer + swap execution fees.

  3. Regarding allox.ai Advanced Techniques

  From what I can observe in the system + TON DEX knowledge:

  The technique you're seeing on allox.ai is likely STON.fi V2 multi-hop 
  routing: TON → pTON → [hop via intermediate token] → target. This is used for
  tokens that only have liquidity against USDT or another jetton (not direct TON
  pair). On STON.fi V2, you can chain pools in a single transaction using a
  referral_address + next_pool_addr pattern in the forward payload.

  What our system is missing:
  - STON.fi V2 support (newer router address)
  - Multi-hop routing for tokens without a direct TON pool
  - Quote comparison: STON.fi v2 vs DeDust before executing (best price routing)
  - The allox.ai "after swap" step is likely a referral/fee split + confirmation
  that the swap landed in V2
